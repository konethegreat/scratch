# SA-JAS — South African Job Agent Suite

## What this is

A three-agent desktop automation suite for the South African job market. It scrapes live job listings, rewrites your CV/cover letter with AI, and guides you through application form submission via a visible browser copilot.

Packaged as an **Electron desktop app** + React frontend + Express backend.

## The three agents

| # | Name | What it does | Key tech |
|---|------|--------------|----------|
| 1 | **Job Hunter** | **Primary engine: Claude grounded web search** (`jobSearchAI.js`, Anthropic `web_search_20250305` tool, SA-localized) — returns real vacancies with real source URLs, no brittle CSS. The AI prompt **biases toward major boards/ATS** (LinkedIn, PNet, Indeed, CareerJunction, Greenhouse/Lever/Workday/…) and **tags each result with its real source** (derived from the URL host via `sourceFromUrl`), surfacing majors first. **Fallback: 12 SA scrapers, major boards first** (LinkedIn, Indeed SA, PNet, CareerJunction, then Google Jobs, Adzuna SA, Executive/Job Placements, National Government, JobMail, Jobs.co.za, Gumtree SA) each with a universal schema.org/JobPosting (JSON-LD) fallback. **Careers24 was removed** — its scraper was unreliably bot-walled. Token-aware keyword scoring 0–100; saves only ≥ 18. Lenient SA-location filter (rejects only explicitly foreign places). Fresh page per source; user can stop mid-run. | Anthropic web search + Playwright |
| 2 | **Document Tailor** | Tailors base CV + writes 300–400 word cover letter per job, ATS-optimised, SA English. Injection-hardened prompts. Also renders the tailored CV and cover letter to **PDF** (via Playwright `page.pdf`) for upload. Provider call shared with Agent 3 via `agents/llm.js`. **T4: accepts an optional `{ researchBrief }`** (grounded employer/role findings) injected into its cached `cvSystem` + cover-letter prompt; can be tailored in **parallel batches** via `subAgents.js`. | Gemini / Anthropic / OpenRouter (swappable) |
| 3 | **Apply Copilot** | Launches visible Chromium at `applyUrl`, runs DOM injection scanner, injects a **persistent** floating HUD that survives navigation and follows new tabs/popups. **Supervised autonomy** (human-on-the-loop): an **Auto-pilot** mode (default ON) that auto Smart-fills + auto-attaches each new form page and auto-clicks **Apply / I'm interested / Continue / Next** to walk multi-step flows — but **never clicks the final Submit** and pauses on any verification. Also: basic autofill, manual **AI Smart-fill** (LLM maps form labels → profile + declared answers, drafts free-text screening answers), **auto-attach CV PDF** (`setInputFiles`), **auto-attach supporting documents** (matches each file field's label/name/accept to the user's stored ID / matric / degree / academic-record PDF and attaches the right one), **PDF-only guard** (only files whose extension AND `%PDF` magic bytes check out are ever uploaded — a markdown/text CV can never be submitted in place of a PDF), **CAPTCHA/anti-bot detect-and-handoff** (never auto-solves), login-wall pre-flight, and **submission-confirmation detection** (screenshots proof, auto-marks applied). Polls until user submits or confirmation is detected. **T3: optional computer-use finisher** (`computerUse.js`) — when `useComputerUse` is on (Anthropic only), after smart-fill it lets Claude *see and operate* the live form via the `computer_20251124` tool to complete tricky/custom fields; never submits (hard coordinate hit-test refuses submit controls), stops on CAPTCHA, step-capped. | Playwright — persistent Chrome/Chromium + `llm.js` (any provider key) + Anthropic computer-use (opt-in) |

All three agents are **fire-and-forget** — the HTTP endpoint responds immediately and the client tracks progress by polling `/api/logs` (every 3 s) and `/api/jobs`.

## Data storage — four locations

### `db.json`
Persists everything except API keys. In dev: project root. In packaged Electron: `app.getPath('userData')/db.json` (injected via `DB_PATH` env var by `electron/main.js`).

Key sections:
- `profile` — AI provider, personal info, search criteria (`keywords`, `locations`, `maxKeywords`, `maxLocations`, `useAiSearch`, `aiSearchModel`, `useLinkValidation` (drop confirmed-dead links, default ON), `useLinkRepair` (AI find-missing-links, default OFF), `useAiPlanner`, `useVision`, `useStructuredOutputs`, `usePromptCaching`, `useMemoryReflection`, `useDreaming` (T2), `useComputerUse`/`computerUseModel`/`computerUseMaxSteps` (T3), `tailorConcurrency`/`useResearchFanout` (T4), **T6:** `searchDepth` ('light'|'standard'|'deep', default 'standard'), `performanceMode` (last APPLIED preset: 'saver'|'balanced'|'max'|'custom' — the UI highlights `performanceModeActual` computed by `detectActivePreset` instead, so manual tweaks honestly read as Custom), `dailyBudgetUSD` (0 = no cap; sanitised in `saveProfile`, max 1000)), `applicationProfile` (structured questionnaire answers for SA forms — see below), `applicationDefaultsText` (free-text catch-all), base CV (no keys). NOTE: all toggles are now persisted through `POST /api/profile` (the earlier explicit whitelist dropped `useStructuredOutputs`/`usePromptCaching`/`useMemoryReflection` — fixed)
- `jobs` — array of job objects
- `supportingDocuments` — metadata for the user's reusable PDFs (the bytes live on disk in `SUPPORTING_DOCS_PATH`). Stored at the **db root** (NOT inside `profile`, so a profile save can't clobber it), keyed by doc-type: `{ [key]: { fileName, originalName, uploadedAt, size } }`. Doc-type keys/labels/field-match regexes are defined once in `SUPPORTING_DOC_TYPES` (helper.js): `id` (ID/passport), `matric` (Grade 12 / NSC), `degree` (degree/diploma), `academicRecord` (statement of results/transcript). Helpers: `getSupportingDocuments` (returns every slot + uploaded flag), `saveSupportingDocument({docType,originalName,dataBase64})` (validates `%PDF`, writes `<key>.pdf`), `deleteSupportingDocument`, `getSupportingDocPath` (returns the path only if it's a real PDF on disk). PDF validation helpers: `isPdfBuffer`, `isRealPdfFile`. Managed via `/api/documents` (NOT the profile form), so uploads persist instantly
- `answerBank` — learn-as-you-go Q&A `{ id, question, normalized, answer, createdAt, updatedAt }`; Agent 3 reuses these across sites by normalized question text. Bulk-clear via `clearAnswerBank` (Danger Zone)
- `pendingQuestions` — questions Agent 3 captured but couldn't answer `{ id, question, normalized, jobId, seenAt }`; surfaced in Settings for the user to answer once. Bulk-clear via `clearAllPending` (Danger Zone)
- `candidateMemory` — the **evolving candidate dossier**, grown with every application and read (as a compact digest) by all three agents. `{ version, updatedAt, insights:[{id,text,category,source,createdAt}], employers:[{id,company,normalized,notes:[string],applications,updatedAt}], applications:[{id,jobId,title,company,appliedAt,outcome,salarySnapshot:{current,expected},transcript:[{question,answer}]}] }`. `insights` come from manual entry or AI **reflection** (`memoryReflect.js`) after a confirmed apply; `employers` are per-company notes; `applications` is an outcome log the user marks applied→interview→offer/rejected (the signal for "which phrasings won"). Distinct from `answerBank` (reusable per-field answers). Insight categories: preference, strength, achievement, style, constraint, other. Helpers: `getCandidateMemory`, `addInsight`, `deleteInsight`, `upsertEmployerNote`, `recordApplication`, `updateApplicationOutcome`, `clearCandidateMemory`, `buildMemoryDigest({company,maxInsights})` (the prompt-ready digest)
- `routines` (T1) — array of unattended recurring runs `{ id, name, enabled, type:'hunt'|'hunt_and_tailor'|'dream', schedule:{frequency:'daily'|'weekdays'|'every_n_hours', timeOfDay, everyHours}, autoTailorCount, catchUp, createdAt, lastRun, lastStatus, lastResult }`. Driven by `routineRunner.js`. Caps: ≤20 routines, autoTailor ≤10, every_n_hours floor 1h. **Routines NEVER run Agent 3 / never submit.** Helpers: `getRoutines`, `getRoutine`, `addRoutine`, `updateRoutine`, `deleteRoutine`, `setRoutineRunState`, `ROUTINE_TYPES`, `ROUTINE_FREQUENCIES`
- `candidateMemory` — insights now carry `weight` (1–10) + `lastConfirmedAt`; `buildMemoryDigest` sorts by weight desc so winning phrasings surface. Added `lastDream` (`{at,added,reinforced,pruned}`). New helpers: `reinforceInsight(idOrText,by)`, `recordDreamResult(...)`
- `hunterState` — `{ isRunning, startedAt, finishedAt, stopRequested, lastResult }` where `lastResult = { totalFound, totalSaved, perSource, stopped }`
- `applyState` — `{ isRunning, jobId, startedAt }`
- `usage` (T6) — the AI usage ledger: `{ days: { 'YYYY-MM-DD': { calls, inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, webSearches, estCostUSD, byBucket: { [bucket]: same-shape } } } }`. Buckets: ai-search, link-repair, tailor, smart-fill, planner, vision, computer-use, research, referral, memory, core. Written by `addUsage` from EVERY AI call (best-effort, never throws); pruned to ~35 days; estimated cost via `db/costs.js`. `budgetStatus()` compares today's `estCostUSD` to `profile.dailyBudgetUSD` — when exceeded, every AI entry point refuses with `budgetMessage()` until midnight
- job objects may also carry `tailoredCvPath`, `tailoredCoverLetterPath`, `confirmationShotPath`, `appliedAt`, and `referral` (T5 outreach channel: `{ contact:{full_name,exact_role,company,profile_url,grounded}, message, grounded, generatedAt }`)

### `keys.json`
API keys only — stored separately from `db.json` so they are never shipped inside the ASAR or the `extraResources` bundle. In dev: project root. In packaged Electron: `app.getPath('userData')/keys.json` (injected via `KEYS_PATH` env var).

- Contains: `geminiApiKey`, `anthropicApiKey`, `openRouterApiKey`
- Auto-migrated from old `db.json` on first run if keys are found there
- `getProfile()` merges `db.json` profile + `keys.json` transparently — callers see one object
- **Never put real keys in `.env`** — `.env` only carries `PORT`. The `.env` fallback for keys was removed; the UI is the only input path.

### `browser-profile/`
Persistent Playwright browser session data. In dev: project root. In packaged Electron: `app.getPath('userData')/browser-profile/` (injected via `BROWSER_PROFILE_PATH` env var).

- Used by Agent 1 (headless scraping) and Agent 3 (visible apply session)
- Both agents call `chromium.launchPersistentContext(BROWSER_PROFILE_PATH, ...)` — tries `channel: 'chrome'` (real Chrome, DPAPI-encrypted cookies on Windows) first, falls back to bundled Chromium
- Populated once via Profile & Settings → "Open login browser" button → user signs into LinkedIn, Indeed, etc. manually → sessions saved for all future runs
- `setupBrowserSession()` exported from `agent1-hunter.js`, triggered by `POST /api/browser/setup`

### `supporting-docs/`
The user's reusable application documents — ID/passport, matric certificate, degree/diploma, academic record — uploaded once and attached by Agent 3 to matching upload fields. In dev: project root. In packaged Electron: `app.getPath('userData')/supporting-docs/` (injected via `SUPPORTING_DOCS_PATH` env var by `electron/main.js`).

- **PDF-only.** Files are validated at upload (`%PDF` magic bytes, `saveSupportingDocument`) and again at attach time (`getSupportingDocPath` → `isRealPdfFile`), so a markdown/text file can never be uploaded to a portal in place of a PDF.
- Stored as `<docType>.pdf` (`id.pdf`, `matric.pdf`, `degree.pdf`, `academicRecord.pdf`); metadata in `db.json` → `supportingDocuments`.
- Uploaded via the **Supporting Documents** panel in Settings (base64 data-URL → `POST /api/documents`). Gitignored (the user's PII never enters the repo or the bundle).

### Logs
Kept **in memory only** (rolling 200-entry array in `helper.js`). Not written to disk.

Helper functions exported from `server/src/db/helper.js`:
`readDb`, `writeDb`, `getProfile`, `saveProfile`, `clearKey`, `getJobs`, `addJob`, `updateJob`, `deleteJob`, `clearAllJobs`, `getLogs`, `addLog`, `clearLogs`, `getHunterState`, `setHunterState`, `getApplyState`, `setApplyState`, `getAnswerBank`, `upsertAnswer`, `deleteAnswer`, `clearAnswerBank`, `getPendingQuestions`, `addPendingQuestion`, `resolvePending`, `clearPending`, `clearAllPending`, `normalizeQuestion`, `getSupportingDocuments`, `saveSupportingDocument`, `deleteSupportingDocument`, `getSupportingDocPath`, `isPdfBuffer`, `isRealPdfFile`, `SUPPORTING_DOC_TYPES`, `getCandidateMemory`, `addInsight`, `deleteInsight`, `upsertEmployerNote`, `recordApplication`, `updateApplicationOutcome`, `clearCandidateMemory`, `buildMemoryDigest`, `INSIGHT_CATEGORIES`, `BROWSER_PROFILE_PATH`, `GENERATED_DOCS_PATH`, `SUPPORTING_DOCS_PATH`

## Job status lifecycle

```
found → tailoring → tailored → applied
```

- `found` — scraped by Agent 1 or added manually
- `tailoring` — Agent 2 in progress (set immediately when tailor is triggered)
- `tailored` — CV saved (cover letter may or may not be present; CV is saved first)
- `applied` — Agent 3 confirmed submission; `appliedAt` ISO timestamp also set

If Agent 2 fails before saving any CV, status reverts to `found`. If it fails after saving the CV (e.g. cover letter API error), it stays `tailored` — partial result is preserved.

## AI providers

Keys entered via the Profile & Settings UI tab only — saved to `keys.json`. No `.env` fallback.

- **Gemini** — default. Model: `gemini-1.5-flash`
- **Anthropic** — Model: `claude-3-5-sonnet-latest`
- **OpenRouter** — proxy for many models. Model: `deepseek/deepseek-chat` (free)

Custom model overrides supported via the "Specific model" field in the UI.

### Structured outputs & prompt caching (Anthropic only)

Two cost/reliability features live in `agents/llm.js`, both **user-toggleable in Settings** (default ON) and applied only on the Anthropic provider:

- **Structured outputs** (`profile.useStructuredOutputs`): `callLlm(profile, prompt, { schema })` sends `output_config: { format: { type: 'json_schema', schema } }` — constrained decoding that guarantees schema-valid JSON (no beta header needed; supported on Haiku 4.5 / Sonnet 4.6 / Opus). Used by Agent 3 smart-fill (`SMARTFILL_SCHEMA` → `{ fills: [{fid,value}] }`, converted back to a mapping; a flat-object fallback keeps the toggle-off path working) and the planner `planPage` (`PLAN_SCHEMA` in `pageBrain.js`). Schemas need `additionalProperties:false` and listed `required`; dynamic-key objects are NOT allowed (hence the `fills` array shape).
- **Prompt caching** (`profile.usePromptCaching`): `callLlm(profile, prompt, { system, cacheSystem: true })` marks the system block with `cache_control: { type: 'ephemeral' }`. Agent 2 puts the injection shield + base CV into one cached system block (`cvSystem`) shared by the CV and cover-letter calls and across every job — base CV is no longer inlined in the user prompt. Caches at ~10% of input cost. **Caveat:** Haiku's cache minimum is ~2048 tokens, so a short base CV won't cache on Haiku (silently, no error); it activates on Sonnet/Opus (1024 min) or with a longer CV. `callLlm` logs `Prompt cache: N read, M written` (type `system`) when a hit/write occurs.

`callLlm` signature is now `callLlm(profile, prompt, { maxTokens, schema, system, cacheSystem })`. Gemini/OpenRouter ignore `schema`/`cacheSystem` and fold `system` into the prompt/messages. `llm.js` imports `addLog` from `db/helper.js` (no circular dep).

## Routines (T1), Dreaming (T2), computer-use (T3), parallel sub-agents (T4) & referral pipeline (T5)

- **Routines (T1, `routineRunner.js`)** — a **dependency-free** scheduler (60 s `setInterval` tick + an 8 s startup catch-up pass). `isDue(routine, now)` is a pure function over the clock: `daily`/`weekdays` fire once past `timeOfDay` if not already run since that slot (implicit catch-up; `catchUp:false` only fires within a 90-min window); `every_n_hours` fires on interval (1 h floor). One routine runs per tick, one at a time (module `busy` flag), and a routine **defers** (status `skipped`) if a manual hunt/apply is in progress — unattended work never collides with the user. `hunt` runs Agent 1; `hunt_and_tailor` then auto-tailors the top `autoTailorCount` NEW jobs (snapshot-diff of job IDs, skipped silently w/o a key) — **concurrently via `tailorJobsConcurrently` (T4), bounded by `tailorConcurrency`**; `dream` runs the Dreaming pass. **Routines never run Agent 3 / never submit** — enforced in `ROUTINE_TYPES` and the runner. Best-effort: errors are caught and recorded on the routine, never crash the server. Started from `index.js` `app.listen`.
- **Dreaming (T2, `dreamOverMemory()` in `memoryReflect.js`)** — a periodic curation pass over the WHOLE dossier (distinct from per-application `reflectOnApplication`). Reads the application outcome log + win transcripts and returns `{reinforce:[idx], prune:[idx], add:[{text,category}]}` (DREAM_SCHEMA on Anthropic; provider-agnostic via `callLlm`). Reinforce bumps insight `weight`; **prune never removes `source:'manual'` insights and is capped at half** the snapshot; adds land at weight 2. Gated by `profile.useDreaming` (default ON), key-skip silent, and an `insufficient-data` short-circuit (no call when there's nothing to learn). Triggers: a `dream` routine, the **Reflect now** button (`POST /api/memory/dream`), or directly.
- **Parallel sub-agents (T4, `pool.js` + `subAgents.js` + `companyResearch.js`)** — turns serial tailoring into bounded parallel bursts. `pool.js` is a **dependency-free** concurrency pool: `mapPool(items, worker, n)` runs ≤`n` workers at once, returns results in original order each shaped `{ok,value}`/`{ok:false,error}` so one failure never aborts the batch; `resolveTailorConcurrency(profile)` clamps `profile.tailorConcurrency` to **1–5** (this is the cost cap and the hook for a future tier gate). `subAgents.js` `tailorJobsConcurrently(jobIds,{concurrency,trigger})` runs in two phases: **(1) research fan-out** — if `useResearchFanout` is on, `mapPool`s `researchCompany()` over the jobs so the slow web-search step overlaps; **(2) tailor fan-out** — `mapPool`s `runDocumentTailorAgent(id,{researchBrief})` so each Agent 2 call reuses its pre-fetched brief (no double research). Batches are **hard-capped at 10 jobs**; it sets each job to `tailoring` up front and reverts to `found` only if nothing was saved (mirrors the single-job route). **`companyResearch.js`** `researchCompany(profile, job)` returns a compact grounded brief (employer sector, recent news, role priorities, SA salary context) via the Anthropic server-side `web_search` tool — **Anthropic-only**, `max_uses:3`, **best-effort (`''` on any failure / when disabled / keyless)**, gated by `researchFanoutReady()` (`useResearchFanout` true AND a real Anthropic key). The brief is threaded into Agent 2's cached `cvSystem` and referenced by the cover-letter prompt's "Why this company" guideline. **Consumers:** the `hunt_and_tailor` routine (replaces its serial auto-tailor loop) and `POST /api/jobs/tailor-batch` (+ a "Tailor all found" button in the Hunter tab). **T4 never runs Agent 3 / never submits** — same human-on-the-loop guarantee. Pure pool logic is unit-tested (order preservation, per-item error isolation, peak-concurrency bound, clamping).
- **Computer-use (T3, `computerUse.js`)** — `computerUseFillForm(page, profile, job)` runs an Anthropic computer-use agentic loop (`computer_20251124` tool, beta header `computer-use-2025-11-24`, default model `claude-sonnet-4-6`, overridable) bound to the existing Playwright page. It runs as a **finisher after** the DOM `smartFillForm` (which stays the cheap, memory-capturing default), completing tricky/custom fields. Coordinates are mapped image-px → CSS-px via `devicePixelRatio`. **Submit-safety is enforced in code, not just the prompt:** every click is hit-tested with `document.elementFromPoint` and refused if the control text matches `SUBMIT_RE` (submit/send/apply-final/pay/finish/confirm) — a coordinate click can't bypass it. Stops on CAPTCHA text and is bounded by `computerUseMaxSteps` (1–25, default 12). Anthropic-only, `useComputerUse` default OFF (most token-hungry). Wired into Agent 3 via a local `fillForm(p)` helper used by both autopilot and the manual Smart-fill button. Pure helpers (`isSubmitText`, `mapKey`, `pngDimensions`, `computerUseSupported`) are unit-tested.
- **Referral pipeline (T5, `referralAgent.js`)** — the post-application **"Direct Outreach Channel"** (a counter-measure to ATS-only screening: open a human-to-human path to technical leadership after applying). `runReferralPipeline(profile, job)` runs two best-effort steps: **(1) `findReferralContact()`** — grounded discovery of ONE senior engineering contact (Engineering Manager → Tech Lead → Team Lead → Head of Eng → CTO) at the applied-to company via the Anthropic server-side `web_search` tool (same engine as `jobSearchAI`/`companyResearch`; `max_uses:3`, ZA-localized, 4-turn pause loop). It returns a normalized `{ full_name, exact_role, company, profile_url, grounded }` and **NEVER invents a person** — if there's no Anthropic key (`groundedReferralReady()` false), the search verifies nobody, or anything throws, it falls back to `{ full_name:'', profile_url: linkedInPeopleSearchUrl(company), grounded:false }` (a pre-filtered LinkedIn people-search link the user follows themselves). **(2) `draftOutreachMessage()`** — a <150-word peer-to-peer message via `callLlm()` (provider-agnostic, honours whichever key is set), referencing the exact role, connecting the user's strongest technical strength (inferred from a capped `baseCv` excerpt + `keywords`) to the company, and ending with a CTA to `portfolioUrl`/`linkedInUrl`; a minimal non-empty template is used on failure so the channel is never blank. **Trigger:** manual only — the **"Find referral contact"** button on `status:'applied'` jobs in the dedicated **Direct Outreach** tab (`ReferralPanel` in `App.jsx`; the Apply Copilot control room links across to it), `POST /api/jobs/:id/referral` (awaited, saves `job.referral`). Cost-controlled by being click-to-run (web search billing) and self-gating to the free LinkedIn fallback without an Anthropic key. **T5 NEVER sends, connects, or messages anyone — it only drafts; the user reviews and reaches out** (same human-on-the-loop guarantee as the rest of the suite). Pure helpers (`linkedInPeopleSearchUrl`, `groundedReferralReady`) are unit-tested.

## Cost controls (T6): performance modes, usage ledger, daily budget & deep search

Built because real-world use was draining the user's API credit. Four cooperating pieces:

- **Performance presets** (`PERFORMANCE_PRESETS` in helper.js, applied via `POST /api/profile/preset`, rendered as `PresetCards` in Settings → AI & Cost): **Token Saver** (AI search on `claude-haiku-4-5` at `searchDepth:'light'`, ALL optional AI off — planner/vision/computer-use/research/link-repair/reflection/dreaming — caching+structured on (free wins), concurrency 1, 2 kw × 1 loc), **Balanced** (the recommended defaults: standard depth, planner+memory+dreaming on, expensive extras off, concurrency 3), **Maximum** (deep 2-round search on `claude-sonnet-4-6`, link repair + research fan-out + vision + computer-use all on, concurrency 5, 5 kw × 3 loc). Presets never touch provider choice, API keys, personal info, CV or answers. `detectActivePreset(profile)` reports which bundle the live values actually match (else `'custom'`) — returned by GET /api/profile as `performanceModeActual` and highlighted in the UI, so a hand-tweaked toggle can't masquerade as a preset. NO preset enables any auto-submit behaviour (unit-tested).
- **Usage ledger** (`addUsage` in helper.js + `db/costs.js` estimator): every AI call from every feature on every provider records tokens/cache/web-searches into per-day, per-bucket tallies with an ESTIMATED USD cost (clearly labelled estimates; provider invoice is ground truth). Rendered by `UsagePanel` (Settings → AI & Cost): est. spend today / last 7 days, tokens in/out, web searches, cache savings, per-feature badges, and a budget progress bar. `GET /api/usage`, reset via `DELETE /api/usage`.
- **Daily budget guard** (`profile.dailyBudgetUSD`, 0 = off): when today's estimated spend reaches the cap, `assertBudget()` in llm.js makes `callLlm`/`callLlmVision` REFUSE (clear log + `BUDGET_EXCEEDED` error), and the raw-SDK call sites (AI search, link repair, company research, referral contact search, computer-use — which also re-checks the cap between steps) skip with the same message. Hard stop until midnight or the cap is raised; the UsagePanel shows a red "budget reached" banner. Best-effort features degrade gracefully (they already catch); a manual Tailor click surfaces the budget message instead of spending.
- **Search depth / deep search** (`profile.searchDepth`, see jobSearchAI.js): the thoroughness dial — `deep` adds a second differently-targeted grounded round per keyword (the fix for "the hunter isn't looking thoroughly"), `light` is the Token-Saver setting. Echoed as a `depth:` badge in the Hunter tab's "Next run" strip.

## Security model

- `keys.json`, `browser-profile/`, `generated-docs/` and `supporting-docs/` are **gitignored** — never commit them (`supporting-docs/` holds the user's ID/qualification PDFs — sensitive PII).
- **T6 hardening:** (1) `addLog` runs every message through `scrubSecrets` — anything shaped like an Anthropic/OpenRouter/Google API key is replaced with `•••redacted-key•••` before it reaches the UI log buffer or stdout (belt-and-braces against SDK error messages echoing a key). (2) `keys.json` is written with POSIX mode `0600` (no-op on Windows, tighter elsewhere). (3) Supporting-document uploads are capped at **15 MB** in `saveSupportingDocument` on top of the `%PDF` magic-byte check. (4) Every Danger-Zone bulk clear first snapshots db.json to `db.backup.json` (`backupDb`, 60s debounce so "Clear everything"'s four parallel clears keep ONE pre-clear snapshot) — restorable via Settings → Documents & Data → "Restore last backup" (`POST /api/backup/restore`). (5) The API binds to `127.0.0.1` (loopback only), not 0.0.0.0.
- API keys travel only via the UI → `saveProfile()` → `keys.json`. The `process.env.*` fallbacks for keys were removed from `agent2-tailor.js`.
- `browser-profile/` stores session cookies, not passwords. When `channel: 'chrome'` is used on Windows, cookies are DPAPI-encrypted (tied to the local Windows user account).
- Agent 3 passes only `{ title, company, tailoredCvText, tailoredCoverLetterText, autofill, injectionWarnings, hasCvFile, hasSupportingDocs }` into the HUD `page.evaluate` — `baseCv`, API keys, and the supporting-document file paths/bytes are never sent into the portal page context (`hasSupportingDocs` is a plain boolean used only to render the attach button; the actual files are attached on the Node side via `setInputFiles`). (Smart-fill builds its LLM prompt on the Node side, so `baseCv` is used there but never injected into the page.)

## Key implementation notes

- Server uses **ESM** (`"type": "module"` in `server/package.json`). Use `import`/`export`, not `require`. `electron/main.js` intentionally stays CommonJS.
- `DB_PATH`, `KEYS_PATH`, `BROWSER_PROFILE_PATH`, `GENERATED_DOCS_PATH` and `SUPPORTING_DOCS_PATH` env vars are injected by `electron/main.js` → `startServer()` (all under `app.getPath('userData')`). In dev they fall back to the project root.
- **Electron window loading (`electron/main.js`) — blank-window hardening**: `isDev = !app.isPackaged` is true for ANY unpackaged launch (`npm run electron:start`, `electron .`), which used to load `http://localhost:4173` even when Vite wasn't running → a silent blank window. `createWindow()` now (1) probes the dev URL with `isUrlReachable()` first and only uses it if actually up; (2) **falls back to the built `client/dist/index.html`** when the dev server is down but a build exists; (3) registers a `did-fail-load` handler + `showLoadError()` that renders a readable error page (with the "run `npm run electron:dev`" hint) instead of leaving the window blank; (4) wraps the load in try/catch so a rejected load promise can't become an unhandled rejection. **For dev, always use `npm run electron:dev`** (starts Vite + Electron together via `wait-on`); standalone Electron now falls back to `dist/` instead of going blank. `client/dist/` must be built (`npm run build:client`) for the packaged/fallback path.
- **Single React instance (`client/vite.config.js`)**: `optimizeDeps.include: ['react','react-dom','react-dom/client','react/jsx-runtime','react/jsx-dev-runtime']` + `resolve.dedupe: ['react','react-dom']`. This pre-bundles every React entry point in **one** optimize pass so react and react-dom can't land on mismatched dep-optimization generations — the cause of a runtime **"Invalid hook call / Cannot read properties of null (reading 'useState')"** crash (white screen) that came from a stale `client/node_modules/.vite` cache serving react and react-dom under different `?v=` hashes (different React instances → null hook dispatcher). If it recurs: stop the dev server, `rm -rf client/node_modules/.vite`, restart (changing `vite.config.js` also auto-invalidates that cache on next start). Electron's renderer caches modules like a browser, so apply fixes by **restarting** the Electron session, not just reloading.
- Agent 1 uses a **fresh page per source** — a bot-block on Careers24 does not affect the page context used by Indeed or LinkedIn. Page timeout is 20 s. Page title is logged after each navigation to detect Cloudflare blocks or login redirects. Card count below the score filter and rejected non-SA count are logged separately.
- **Link validation (`linkValidator.js`, Agent 1) — conservative, keep-on-doubt**: before any job is saved (both the AI-search phase and the scraper phase), candidate links pass through `validateJobs()`. The design principle is **trust the grounded search; only remove what is provably useless** — never throw away a good job because a bot-wall or an unusual URL shape made it hard to verify. **One owner of link policy** (jobSearchAI no longer blanks URLs). Behaviour: (1) `classifyPostingUrl(url)` is a **lenient** shape check — it returns false only for clear non-postings (bare domain, `?q=`/`search=`, `/search|/browse|/results`, `"/in-place"` category with no id); a real posting URL of almost any board shape passes (e.g. a LinkedIn `/jobs/view/<slug>-<id>` passes because it carries an id). (2) `probeLink(url)` is a liveness fetch (follow redirects, browser UA) that declares **`dead` only on a high-confidence signal — HTTP 404/410/451 or an explicit "expired/filled/closed/no-longer-available" page**; every other non-2xx (401/403/405/429/5xx/999), timeout, network error, or ambiguous redirect-to-home/search is kept as `linkStatus:'unverified'`. **Drop/keep rules:** a job is DROPPED only when its link is confirmed dead; a search/category "link" has its URL **stripped** and the job is kept as a **linkless lead** (`linkStatus:'no-link'`, so Agent 3 won't open it and can't wander); everything else is kept (`live`/`unverified`). Kept jobs gain `linkStatus` + `linkCheckedAt`, surfaced as a green **Verified** / amber **Unverified** `LinkBadge` on job cards (Dashboard, Hunter table, Tailor detail; `no-link`/unchecked render no badge). Bounded concurrency via `pool.js` `mapPool`; best-effort (returns jobs unvalidated on its own failure, and a single worker error keeps that job flagged `unverified` rather than losing it). Gated by `profile.useLinkValidation` (default ON; Settings toggle "Verify job links before saving"); with liveness off it still strips obvious search/category links (free URL hygiene) but probes nothing. **History:** an earlier version of this gate was far too aggressive — strict per-board URL regexes that *blanked* real postings (which then got dropped as "no url"), plus treating any 4xx/5xx/redirect as dead — which gutted the AI search and made the hunter look broken; this rewrite is the fix.
  - **Browser-grade probing**: the hunter creates ONE `createProbeContext()` (a Playwright `request.newContext()` — realistic TLS/headers, no browser window) and threads it through every `probeLink`/`validateJobs` call (both phases), so bot-walls cause far fewer false `unverified` flags than a raw `fetch`. Falls back to Node `fetch` if the context can't be created. Disposed in the hunter's `finally`.
  - **AI link repair (`findDirectPostingUrl`, opt-in)**: when a kept job has **no usable link** (`no-link`), the hunter can ask Claude — grounded web search — for the real posting URL, then **re-validate that URL** before saving (so a hallucinated/dead repair can't slip through). Gated by `profile.useLinkRepair` (default OFF — billed per search) + a real Anthropic key, and hard-capped at `LINK_REPAIR_CAP` (6) repairs per run. Repaired jobs are logged and counted.
  - **Run-level link health**: the hunter returns `linkStats` (`{ live, unverified, noLink, dead, repaired }`) inside `hunterState.lastResult`; the dashboard **RunSummary** renders it as a "Link health:" badge row.
  - **Re-validation (`revalidateJobLinks`, `POST /api/jobs/revalidate`)**: postings die over time, so the user can re-check links of **already-saved** jobs (statuses `found`/`tailored`/`tailoring`) from the **Re-check links** button (Hunter tab). It updates each job's `linkStatus` in place — a now-dead posting is flagged `linkStatus:'dead'` (red **Expired** `LinkBadge`) but **never deleted**; the user decides. Background, browser-grade, idempotent (a `revalidating` in-flight guard returns 409).
- **AI search engine (`jobSearchAI.js`)**: `huntViaClaudeSearch()` runs FIRST in `runJobHunterAgent` (Phase 0), using the Anthropic server-side `web_search_20250305` tool with `user_location` country `ZA`. It's **grounded** — Claude returns real source URLs from its search, and the prompt forbids inventing jobs/URLs; results without an `http(s)` `applyUrl` keep the title but no link. The prompt **strongly prefers major boards/ATS** and asks for the canonical posting page (a board's job page is acceptable) — it deliberately **no longer tells Claude to *drop* a job when the link isn't a perfect direct posting** (that both shrank yield and produced linkless jobs); instead it returns the job with `applyUrl:""` and the downstream validator decides. Each result's `source` is set from its URL host (`sourceFromUrl` → LinkedIn/PNet/Indeed/Greenhouse/…, else the employer domain) so obscure aggregators are visible, and results are **sorted major-board-first** (`boardRank`) so they win de-duplication. Requires `profile.anthropicApiKey` (independent of the tailoring provider). Gated by `profile.useAiSearch` (default true); model `profile.aiSearchModel` (default `claude-sonnet-4-6`). Billed ~$10/1,000 searches; `max_uses: 5` per keyword, up to **20 results** per keyword. The Playwright scrapers run after as best-effort fallback.
- Agent 1 keyword scoring is **token-aware** (`calculateMatchScore`): a multi-word keyword scores on the full phrase AND its individual words (title > description), so "Software Engineer" matches "Senior Engineer"/"Software Developer". Threshold is **≥ 18** (`SCORE_THRESHOLD`) so a single relevant title word passes. The earlier exact-phrase-only matching + threshold 25 filtered out almost everything (especially empty-description sources).
- After each source's bespoke CSS scrape, Agent 1 runs `scrapeJsonLd()` against the same loaded page to harvest any embedded **schema.org/JobPosting** structured data. This is a resilience net against CSS class churn. Skipped for Google Jobs and Govt SA (no JobPosting JSON-LD).
- SA-location filtering is now **lenient for all sources**: LinkedIn/Google are already SA-geo-locked by their query, so the filter only rejects when a foreign place is **explicitly named** (`FOREIGN_LOCATION_TERMS`). Unknown/unlisted suburbs pass — this fixed the over-filtering that dropped valid SA jobs in smaller towns. (`isSouthAfricanLocation(loc, strict=false)`.)
- Run breadth is capped by `profile.maxKeywords` (default 3) and `profile.maxLocations` (default 2), both editable in Profile & Settings. `oncePerKeyword` / `noLocation` sources ignore the location loop.
- **Cancellation**: `hunterState.stopRequested` is checked between sources and keywords. `POST /api/jobs/hunter/stop` sets it; the run winds down and reports `{ stopped: true }` plus a per-source saved breakdown in `lastResult.perSource`.
- **CORS** is locked to localhost/127.0.0.1 origins (plus no-Origin Electron renderer requests) in `index.js` — not wide-open.
- Agent 2 prompts begin with an **injection shield** that instructs the model to treat any directives found inside the job description as plain text, not commands. The job description block is wrapped with `[BEGIN UNTRUSTED JOB DESCRIPTION]` / `[END UNTRUSTED JOB DESCRIPTION]` markers.
- Agent 3 runs a **DOM injection scanner** (`page.evaluate`) before injecting the HUD. It walks all leaf nodes looking for hidden elements (display:none, visibility:hidden, opacity < 0.1, font-size < 2 px) whose text matches known injection patterns. Findings are logged to the Activity Console and displayed as a red warning section at the top of the HUD.
- Google Jobs entries always have `applyUrl: ''` — the public search page does not expose a direct apply link. Agent 3 will reject them with a clear error message.
- Agent 3 requires both a non-empty `applyUrl` AND a non-empty `tailoredCvText` before launching any browser.
- **CAPTCHA / anti-bot policy (Agent 3)**: challenges are **detected, never solved**. `detectChallenge()` only fires on a **visible, interactive-sized** challenge (a sized iframe/widget) or visible challenge text — it deliberately ignores invisible reCAPTCHA v3 badges. (Earlier a blind frame-URL match false-positived on those site-wide badges and paused autopilot forever; fixed.) On detection the copilot logs it, shows a HUD banner, `bringToFront()`s the window, and keeps the session alive until the human clears it. Auto-solving is deliberately avoided — it risks bans on the user's real logged-in accounts and violates site terms.
- **Agent 3 session hardening (verified live):** (1) the apply poll-loop breaks as soon as `context.pages()` has no live page, so closing the copilot window ends the session and resets `applyState.isRunning` within seconds instead of hanging for the 20-min timeout; (2) on navigation Agent 3 warns (`addLog` error) when the landing page looks like an expired/removed advert — a results heading starting with "0 ..." or "no jobs/results found" etc. (expired AI-search links often 302 to an empty search); (3) it reuses the persistent context's default page (`context.pages()[0]`) instead of opening a second tab (no more stray `about:blank`).
- **Agent 2 output sanitisation:** `stripFences()` removes a leading ```` ```lang ```` and trailing ```` ``` ```` that models sometimes wrap the whole document in, before saving/PDF render — otherwise the fences printed literally in the cover-letter PDF.
- **Persistent HUD (Agent 3)**: the HUD is injected via `injectHud(page, hudData)` (idempotent — bails if `#sajas-copilot-hud` already exists) and re-injected on every `page.on('load')`. `context.on('page')` follows new tabs/popups (e.g. PNet's "I'm interested" opening the application in a fresh tab) — it sets `activePage`, attaches the load handler, and injects the HUD there. The polling loop always operates on `activePage`, so the copilot no longer vanishes when a portal navigates. `scanInjections()` is extracted so the injection scan also re-runs on each new page.
- **Auto-pilot (Agent 3)**: a Node-side `autopilot` bool (default ON), toggled from the HUD (`window.sajasAutopilotToggle` flag → Node flips it → `window.sajasSetAutopilot()` pushes state back). When ON and no challenge is up: it first calls `isApplicationForm(p)` — **it only `smartFillForm()`s pages that are genuinely application forms** (file/email input, or ≥4 non-search fields incl. a name/phone/cover/etc. field, or a textarea/select + name-ish field). On a listing/search/landing page it types NOTHING and instead runs `findAdvanceButton()` → one auto-click of an Apply/I'm-interested/Continue/Next link to reach the real form. `filledPages`, `advancedKeys` (`url::buttonText`), and `noFormNoted` Sets prevent re-filling, click loops, and log spam. This fixes the bug where it typed the job title into a site search box and never entered the application. **Safety: `findAdvanceButton()` excludes submit/send-application/finish/confirm/pay wording — the final Submit always stays a human click.** Manual Smart-fill/Attach buttons still work regardless of autopilot. Provider-agnostic: `smartFillForm()` routes through `callLlm()`, honouring whichever key (Gemini/Anthropic/OpenRouter) the user selected — Agent 3 is not locked to Claude.
- **Field types (Agent 3 smart-fill)**: extraction now captures `<select>`, **radio groups** (one entry per `name`, `options` carry each radio's value + visible label) and **single checkboxes** (yes/no consent), and **never touches search boxes** (`type=search`, `role=searchbox`, or name/id/placeholder matching `search|query|keyword|find a job`). `applyMapping()` selects radios by value/label match, ticks/unticks checkboxes from yes/no synonyms, matches `<select>` options, and sets text/textarea natively — returning the fids actually filled.
- **Smart-fill — 3 passes (Agent 3)**: `smartFillForm()` now runs (1) a **deterministic** pass that fills fields it recognises from the user's structured `applicationProfile` via `FIELD_DICT` (label/name regex → key) and from the `answerBank` (matched on `normalizeQuestion`), with NO LLM — so demographics/EE/salary/notice are exact, never guessed; (2) an **LLM** pass for whatever is left (free-text screening questions), grounded on the structured profile + bank + `applicationDefaultsText`, injection-hardened (labels untrusted); (3) a **capture** pass that queues any still-empty REQUIRED field into `pendingQuestions` (deduped by normalized text, skipping anything already in the bank) so the user answers it once and it auto-fills forever after. `applyMapping()` handles `<select>` by case-insensitive exact-then-contains option matching and returns the fids actually filled. Used by both the manual Smart-fill button and autopilot.
- **Application questionnaire (Settings)**: `client/src/ApplicationAnswers.jsx` renders the structured questionnaire (dropdowns/inputs for the ~17 recurring SA questions), the free-text catch-all, a **Pending questions** panel (answer → POST resolve → bank), and the **Saved answers** bank (delete). ID/passport number is deliberately NOT collected — pasted per-application. Sensitive fields (EE race/gender/disability, salary, criminal record) are optional and stored locally only.
- **Auto-attach (Agent 3)**: `attachCvFile()` uses Playwright `setInputFiles` to attach `job.tailoredCvPath` (the PDF from Agent 2) to resume/CV-like file inputs. It is **PDF-guarded** (`isRealPdfFile` — checks `.pdf` extension AND `%PDF` magic bytes), skips inputs that already hold a file, and only falls back to "the single file input" when that input isn't clearly some other document — so a lone "ID upload" field never gets the CV by mistake.
- **Auto-attach supporting documents (Agent 3)**: `attachSupportingDocs()` tags every `input[type=file]` with `data-sajas-file`, builds a context string from each field's name/id/aria-label/accept + nearest label, and matches it against `SUPPORTING_DOC_TYPES[].match` (ID → matric → degree → academicRecord, most-specific first). The matching stored PDF (resolved via `getSupportingDocPath`, PDF-verified) is attached; a `usedKeys` set stops the same doc landing in two fields, and resume-like fields are left to `attachCvFile`. Runs alongside the CV attach in autopilot (both fill sites) and on the manual **Attach** button. The HUD attach button is shown when a CV PDF **or** any supporting doc is available, and its label adapts ("Attach CV" / "Attach Documents" / "Attach CV + Documents").
- **Submission confirmation (Agent 3)**: `detectSubmissionConfirmation()` looks for strong confirmation phrases; on match it screenshots the page to `GENERATED_DOCS_PATH` (`<jobId>-confirmation.png`), sets `confirmationShotPath`, and auto-marks the job applied. The copilot never clicks Submit itself.
- **Evolving candidate memory (`candidateMemory` + `memoryReflect.js`)**: a growing dossier all three agents read. **Capture**: `smartFillForm()` takes an optional `transcript` array and pushes every Q&A it actually fills (deterministic + LLM, search boxes excluded); Agent 3 accumulates one `sessionTranscript` across the whole multi-step flow. **Record**: on a confirmed application, Agent 3 calls `recordApplication()` (logs title/company/`appliedAt`/`salarySnapshot`/transcript, bumps the employer's application count) — best-effort, never undoes a confirmed apply. **Reflect**: then `reflectOnApplication(profile,{job,transcript})` runs one injection-hardened LLM call (uses `REFLECT_SCHEMA` on Anthropic; provider-agnostic via `callLlm`) to distil ≤5 durable `insights` + one `employerNote`, written via `addInsight`/`upsertEmployerNote`. Gated by `profile.useMemoryReflection` (default ON, Settings toggle); **skips silently if no provider key**, so the dossier still records history offline. **Consume**: `buildMemoryDigest({company})` produces a compact text block injected into Agent 2's cached `cvSystem` and into Agent 3's smart-fill LLM prompt (employer notes for the target company + recent insights + roles that reached interview/offer + a salary reference). **Learn what wins**: the user marks each application applied→interview→offer/rejected in the Candidate Memory tab (`PATCH /api/memory/application/:jobId`), and interview/offer rows are surfaced in the digest. Insights are deduped by normalized text and capped at 250.
- **Generated docs path**: `GENERATED_DOCS_PATH` (helper.js, injected by Electron, dev fallback `generated-docs/`, gitignored) holds tailored CV/cover-letter PDFs and confirmation screenshots. Job gains `tailoredCvPath`, `tailoredCoverLetterPath`, `confirmationShotPath`.
- Only one apply session can be open at a time (`applyState.isRunning` guard in the route).
- `db.json` deduplicates jobs by `applyUrl` OR `title + company`. **Upgrade-on-duplicate (`addJob`)**: the AI search runs first and often saves a vacancy as a *linkless lead*; when a later source (e.g. a scraper) finds the SAME `title + company` **with a real apply link**, `addJob` no longer silently discards it — it patches the existing still-`found` job's `applyUrl`/`linkStatus`/`source` (and bumps `matchScore` if higher) in place. Never overwrites a tailored/applied job and never downgrades a good link. This was the main cause of saved jobs ending up with no link.
- `App.jsx` is the single file for all frontend state — tabs, polling, modals.
- **Dashboard UX helpers (`App.jsx`)**: `SetupChecklist` shows what's still needed (tailoring key, Anthropic key for AI search, base CV, keywords, locations) and hides itself when ready; `RunSummary` reads `hunterState.lastResult` (via `/api/status`) to show saved/found + per-source breakdown + a plain-language diagnosis when a run saved 0 (AI search off / no Anthropic key / matched nothing). The Job Hunter tab also shows an engine+scope echo ("Next run: engine = AI Search · N of M keywords × …") and the Match column header has a tooltip explaining the 0–100 score.
- `.env` is loaded from `sa-job-agent-suite/.env` (two levels up from `server/src/`). Server also tries `server/.env` as fallback. `.env` carries `PORT` only — no API keys.
- **Exact-posting links + cross-site persistence (Agent 1 + Agent 3)**: two layers keep the copilot from landing on a search/listing page and "wandering looking for a way in". (1) `jobSearchAI.js` prompt now demands the EXACT direct posting URL (with a unique job/posting id) and forbids homepages/category/search pages; a server-side `looksLikeDirectPosting(url)` guard then blanks any `applyUrl` that smells like a search/listing/bare-domain link before it's stored — so a junk link never reaches Agent 3. (2) Agent 3's `findAdvanceButton()` advance-word regex was broadened to follow SA-aggregator hand-offs ("apply on company website", "view & apply", "apply externally", "easy apply", "view/open job/posting", etc.) while the `stopRe` final-submit guard is unchanged — combined with the existing `context.on('page')` new-tab following and per-load HUD re-injection, the copilot stays with the user from the board (LinkedIn/PNet/Careers24) onto the employer's own ATS, all the way to the form, and still never clicks the final Submit.
- **Global Refresh + child refetch (`App.jsx`)**: the header **Refresh** button now calls `refreshAll()`, which reloads profile/jobs/logs/status/documents (all GET fetches send `cache: 'no-store'` to defeat any renderer caching) and bumps a `refreshTick`. `refreshTick` is passed as `refreshSignal` to the self-polling tabs (`ApplicationAnswers`, `CandidateMemory`, `Routines`), which include it in their effect deps so they refetch immediately instead of waiting for their next poll. This fixes "I changed something and Refresh didn't reflect it" (the old button refetched only jobs/logs/status, never the profile).
- **Danger Zone (Settings, `App.jsx`)**: a clear-data section — `clearData('jobs'|'answers'|'pending'|'memory')` each hit a `DELETE` endpoint behind a confirm modal, plus **Clear everything** (`clearEverything`) which clears jobs + answer bank + pending + candidate memory in one `Promise.all`. Profile, API keys and uploaded supporting documents are intentionally preserved.
- **Page understanding — planner + vision (Agent 3)**: a new module `server/src/agents/pageBrain.js` makes auto-pilot comprehend pages instead of relying only on keyword heuristics. `planPage()` sends a compact text summary (title, headings, fillable fields, visible buttons) to the user's LLM and returns `{ pageType, action: fill|click|wait|done, buttonText, confidence, reason }` — one cheap call per URL, capped at `PLANNER_CAP` (25) per session and cached in `plannedUrls`. The autopilot order is: real form → `smartFillForm`; else → planner; else → keyword heuristic. `clickButtonByText()` clicks the planner's named control but **refuses submit/send/finish/confirm/pay wording**, so the planner can never fire the final submit. `lookWithVision()` is an opt-in fallback (only when the planner is low-confidence): it screenshots the page and asks a multimodal model the same question. Gated by `profile.useVision` (default false) and `providerSupportsVision()` (Gemini/Anthropic only; OpenRouter/DeepSeek is text-only and skipped). `llm.js` gained `callLlmVision()` + `providerSupportsVision()`. Profile flags `useAiPlanner` (default true) and `useVision` (default false) are toggled in Settings.
