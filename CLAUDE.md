# SA-JAS — South African Job Agent Suite

## What this is

A three-agent desktop automation suite for the South African job market. It scrapes live job listings, rewrites your CV/cover letter with AI, and guides you through application form submission via a visible browser copilot.

Packaged as an **Electron desktop app** + React frontend + Express backend.

The AI layer is **Anthropic only** (bring your own key). Direction of travel: `docs/superpowers/specs/2026-10-24-sa-jas-v2-master-plan.md` (a draft plan that supersedes `ROADMAP.md`).

## The three agents

| # | Name | What it does | Key tech |
|---|------|--------------|----------|
| 1 | **Job Hunter** | **Primary engine: Claude grounded web search** (`jobSearchAI.js`, Anthropic `web_search_20260318` tool, SA-localized) — returns real vacancies with real source URLs, no brittle CSS. The AI prompt **biases toward major boards/ATS** (LinkedIn, PNet, Indeed, CareerJunction, Greenhouse/Lever/Workday/…) and **tags each result with its real source** (derived from the URL host via `sourceFromUrl`), surfacing majors first. **Fallback: a declarative 12-source registry** (`hunter/registry.js`, major boards first: LinkedIn, Indeed SA, PNet, CareerJunction, then Google Jobs, Adzuna SA, Executive/Job Placements, National Government, JobMail, Jobs.co.za, Gumtree SA), each source carrying `buildUrl`/`extractInPage`/`saCheck`/pagination. The pipeline pages through results via `hunter/crawl.js` at `profile.searchDepth` (light 1 / standard 2 / deep 4 pages, saturation-aware, de-duplicated), then applies the universal schema.org/JobPosting (JSON-LD) fallback per page. Per-source **health + circuit breaker** (`hunter/health.js`, `healthStore.js`) skips broken/disabled/cooling sources, and a silent zero after a good baseline can fall back to the Haiku **page extractor** (`hunter/aiExtract.js`, anchor-verified links, ≤6 attempts/run). **Careers24 was removed** — its scraper was unreliably bot-walled. Token-aware keyword scoring 0–100; saves only ≥ 18. Lenient SA-location filter (rejects only explicitly foreign places). One page per query at light, up to four at deep; a process-wide **browser lock** (`hunter/browserLock.js`) serialises hunts, applies and login checks; user can stop mid-run. | Anthropic web search + Playwright |
| 2 | **Document Tailor** | Tailors base CV + writes 300–400 word cover letter per job, ATS-optimised, SA English. Injection-hardened prompts. Also renders the tailored CV and cover letter to **PDF** (via Playwright `page.pdf`) for upload. Claude call shared with Agent 3 via `agents/llm.js` (uses `callLlmFull`: a CV or cover letter that comes back `truncated` (hit `max_tokens`) or empty is NEVER saved or rendered — the CV throws so the route reverts the job to `found`, the best-effort cover letter is skipped and logged); prompts built by the pure `tailorPrompts.js` so the cached `system` block (injection shield + base CV + company-independent dossier) is identical for every job. **T4: accepts an optional `{ researchBrief }`** (grounded employer/role findings) injected, as untrusted data, into the per-job CV + cover-letter prompts (not the cached system block); can be tailored in **parallel batches** via `subAgents.js`. | Anthropic Claude (`tailor` task, Sonnet 5.5 by default) |
| 3 | **Apply Copilot** | Launches visible Chromium at `applyUrl`, runs DOM injection scanner, injects a **persistent** floating HUD that survives navigation and follows new tabs/popups. **Supervised autonomy** (human-on-the-loop): an **Auto-pilot** mode (default ON) that auto Smart-fills + auto-attaches each new form page and advances multi-step flows under the click policy in `submitGuard.js` / `controls.js` (on a form page only **Next / Continue / Proceed** are clicked and a bare "Apply" is left to you; the wider **Apply / I'm interested** words are used only on listing/landing pages to reach the form) — but **never clicks the final Submit** and pauses on any verification. Also: basic autofill, manual **AI Smart-fill** (LLM maps form labels → profile + declared answers, drafts free-text screening answers), **auto-attach CV PDF** (`setInputFiles`), **auto-attach supporting documents** (matches each file field's label/name/accept to the user's stored ID / matric / degree / academic-record PDF and attaches the right one), **PDF-only guard** (only files whose extension AND `%PDF` magic bytes check out are ever uploaded — a markdown/text CV can never be submitted in place of a PDF), **CAPTCHA/anti-bot detect-and-handoff** (never auto-solves), login-wall pre-flight, and **submission-confirmation detection** (screenshots proof, auto-marks applied). Polls until user submits or confirmation is detected. **T3: optional computer-use finisher** (`computerUse.js`) — when `useComputerUse` is on (Anthropic only), after smart-fill it lets Claude *see and operate* the live form via the `computer_toolset_20260801` toolset to complete tricky/custom fields; never submits (hard coordinate hit-test refuses submit controls), stops on CAPTCHA, step-capped. | Playwright — persistent Chrome/Chromium + `llm.js` (your Anthropic key) + Anthropic computer-use (opt-in) |

All three agents are **fire-and-forget** — the HTTP endpoint responds immediately and the client tracks progress by polling `/api/logs` (every 3 s) and `/api/jobs`. The source health board additionally polls `/api/hunter/sources` every 3 s only while a canary test is running (`testing: true`).

## Data storage — four locations

### `db.json`
Persists everything except API keys. In dev: project root. In packaged Electron: `app.getPath('userData')/db.json` (injected via `DB_PATH` env var by `electron/main.js`).

Key sections:
- `profile` — `schemaVersion` (2; stamped by `migrateProfile`), `selectedModel` (optional model override for the general tasks: '' = use each task's registry default; a legacy Claude ID is migrated to its family's current registry ID, anything else that is not an exact registry ID is reset to ''), personal info, search criteria (`keywords`, `locations`, `maxKeywords`, `maxLocations`, `useAiSearch`, `aiSearchModel` (registry ID or '' for the task default), `useLinkValidation` (drop confirmed-dead links, default ON), `useLinkRepair` (AI find-missing-links, default OFF), `useAiPlanner`, `useVision`, `useStructuredOutputs`, `usePromptCaching`, `useMemoryReflection`, `useDreaming` (T2), `useComputerUse`/`computerUseModel`/`computerUseMaxSteps` (T3; steps clamped to 1–40, default 20), `tailorConcurrency`/`useResearchFanout` (T4), **T6:** `searchDepth` ('light'|'standard'|'deep', default 'standard'), `performanceMode` (last APPLIED preset: 'saver'|'balanced'|'max'|'custom' — the UI highlights `performanceModeActual` computed by `detectActivePreset` instead, so manual tweaks honestly read as Custom), `dailyBudgetUSD` (0 = no cap; sanitised in `saveProfile`, max 1000)), `applicationProfile` (structured questionnaire answers for SA forms — see below), `applicationDefaultsText` (free-text catch-all), base CV (no keys). There is no `aiProvider` field any more (removed by the v2 migration); the provider is always Anthropic. NOTE: all toggles are now persisted through `POST /api/profile` (the earlier explicit whitelist dropped `useStructuredOutputs`/`usePromptCaching`/`useMemoryReflection` — fixed)
- `jobs` — array of job objects
- `supportingDocuments` — metadata for the user's reusable PDFs (the bytes live on disk in `SUPPORTING_DOCS_PATH`). Stored at the **db root** (NOT inside `profile`, so a profile save can't clobber it), keyed by doc-type: `{ [key]: { fileName, originalName, uploadedAt, size } }`. Doc-type keys/labels/field-match regexes are defined once in `SUPPORTING_DOC_TYPES` (helper.js): `id` (ID/passport), `matric` (Grade 12 / NSC), `degree` (degree/diploma), `academicRecord` (statement of results/transcript). Helpers: `getSupportingDocuments` (returns every slot + uploaded flag), `saveSupportingDocument({docType,originalName,dataBase64})` (validates `%PDF`, writes `<key>.pdf`), `deleteSupportingDocument`, `getSupportingDocPath` (returns the path only if it's a real PDF on disk). PDF validation helpers: `isPdfBuffer`, `isRealPdfFile`. Managed via `/api/documents` (NOT the profile form), so uploads persist instantly
- `answerBank` — learn-as-you-go Q&A `{ id, question, normalized, answer, createdAt, updatedAt }`; Agent 3 reuses these across sites by normalized question text. Bulk-clear via `clearAnswerBank` (Danger Zone)
- `pendingQuestions` — questions Agent 3 captured but couldn't answer `{ id, question, normalized, jobId, seenAt }`; surfaced in Settings for the user to answer once. Bulk-clear via `clearAllPending` (Danger Zone)
- `candidateMemory` — the **evolving candidate dossier**, grown with every application and read (as a compact digest) by all three agents. `{ version, updatedAt, insights:[{id,text,category,source,createdAt}], employers:[{id,company,normalized,notes:[string],applications,updatedAt}], applications:[{id,jobId,title,company,appliedAt,outcome,salarySnapshot:{current,expected},transcript:[{question,answer}]}] }`. `insights` come from manual entry or AI **reflection** (`memoryReflect.js`) after a confirmed apply; `employers` are per-company notes; `applications` is an outcome log the user marks applied→interview→offer/rejected (the signal for "which phrasings won"). Distinct from `answerBank` (reusable per-field answers). Insight categories: preference, strength, achievement, style, constraint, other. Helpers: `getCandidateMemory`, `addInsight`, `deleteInsight`, `upsertEmployerNote`, `recordApplication`, `updateApplicationOutcome`, `clearCandidateMemory`, `buildMemoryDigest({company,maxInsights})` (the prompt-ready digest)
- `routines` (T1) — array of unattended recurring runs `{ id, name, enabled, type:'hunt'|'hunt_and_tailor'|'dream'|'canary', schedule:{frequency:'daily'|'weekdays'|'every_n_hours', timeOfDay, everyHours}, autoTailorCount, catchUp, createdAt, lastRun, lastStatus, lastResult }`. Driven by `routineRunner.js`. Caps: ≤20 routines, autoTailor ≤10 (and forced to 0 for non-`hunt_and_tailor` types), every_n_hours floor 1h. A `canary` run stores `lastResult = { canary:<results by source id>, tested, passed, note }`. **Routines NEVER run Agent 3 / never submit.** Helpers: `getRoutines`, `getRoutine`, `addRoutine`, `updateRoutine`, `deleteRoutine`, `setRoutineRunState`, `ROUTINE_TYPES` (`hunt`, `hunt_and_tailor`, `dream`, `canary`), `ROUTINE_FREQUENCIES`
- `candidateMemory` — insights now carry `weight` (1–10) + `lastConfirmedAt`; `buildMemoryDigest` sorts by weight desc so winning phrasings surface. Added `lastDream` (`{at,added,reinforced,pruned}`). New helpers: `reinforceInsight(idOrText,by)`, `recordDreamResult(...)`
- `hunterState` — `{ isRunning, startedAt, finishedAt, stopRequested, lastResult }` where `lastResult = { totalFound, totalSaved, perSource, linkStats, perSourceStats, stopped }` and `perSourceStats[name] = { pages, raw, saved, stopReason, via, status, skipped? }`
- `applyState` — `{ isRunning, jobId, startedAt }`
- `usage` (T6) — the AI usage ledger: `{ days: { 'YYYY-MM-DD': { calls, inputTokens, outputTokens, cacheReadTokens, cacheWriteTokens, webSearches, estCostUSD, byBucket: { [bucket]: same-shape }, byTask: { [taskType]: { runs, failures, calls, estCostUSD, inputTokens, cacheReadTokens, cacheWriteTokens } } } } }`. Buckets are the core task keys: ai-search, link-repair, research, referral-search, referral, tailor, smart-fill, planner, vision, memory, computer-use, core. `byTask` is keyed by the agent-run type given to `withTask` (hunt, tailor, apply, memory-reflect, memory-dream); `runs`/`failures` come from `recordTaskRun`, the rest from `addUsage` for calls made inside that run. ## Job status lifecycle

```
found → tailoring → tailored → applied
```

- `found` — scraped by Agent 1 or added manually
- `tailoring` — Agent 2 in progress (set immediately when tailor is triggered)
- `tailored` — CV saved (cover letter may or may not be present; CV is saved first)
- `applied` — Agent 3 confirmed submission; `appliedAt` ISO timestamp also set

If Agent 2 fails before saving any CV, status reverts to `found`. If it fails after saving the CV (e.g. cover letter API error), it stays `tailored` — partial result is preserved.

## Error contract (M3a-1)

Every failure — the desktop API, the core AI layer, and the client — uses one
shape:

```js
{ error, message, code, hint, retryable, requestId, details? }
```

`error` is the legacy alias and equals `message`. `requestId` is `local-…`:
the server generates it in `server/src/httpErrors.js` and returns the same value
in `X-Request-Id`; the client generates one when it maps a local failure.

Codes: `KEY_INVALID`, `KEY_ADMIN`, `AUTH_REJECTED`, `KEY_PERMISSION`,
`SPEND_CAP`, `RATE_LIMITED`, `OVERLOADED`, `BUDGET_EXCEEDED`,
`NETWORK_OFFLINE`, `CORS_BLOCKED`, `STORAGE_FULL`, `STORAGE_UNAVAILABLE`,
`FEED_FAILED`, `VALIDATION`, `NOT_FOUND`, `CONFLICT`, `FORBIDDEN`,
`NOT_SUPPORTED_IN_WEB`, `UNKNOWN`.

- `packages/core/src/errors.js` owns `ERROR_CODES`, `AppError`, the catalog of
  user-facing messages/hints/statuses, `statusForCode` and `toUserError`. It
  maps SDK statuses (401/403/429/529/5xx), key errors, connection failures
  (offline vs CORS), storage errors, budget refusals and already-shaped bodies.
  Import it in the browser via the `@sajas/core/errors` subpath — never the
  package root, which pulls in the SDK.
- `server/src/httpErrors.js` owns `requestContext`, `sendError`, the
  `badRequest`/`notFound`/`conflict`/`forbidden` helpers and the terminal
  `errorHandler`. Every route failure goes through it; do not hand-write
  `res.status(...).json({ error })` in a route again.
- `client/src/errors.js` parses responses (`readResponseError`,
  `contractFromBody`), keeps the last 20 failures in memory and builds
  copyable diagnostics. `ErrorCard` shows cause, hint, Retry when the code is
  retryable and the view supplies a retry handler, Details only when the payload
  carries `details`, and Copy diagnostics; `ErrorBoundary` catches render
  crashes; the Activity Logs tab lists recent errors.
- Messages, hints and details are scrubbed with `scrubSecrets` before they
  leave the core, the server or the client. Server `details` never contains a
  stack trace.

## Web mode

`npm run build:web` (from `sa-job-agent-suite/`) is `vite build --mode web`.
`client/vite.config.js` defines `__SAJAS_WEB__` at compile time; there is no
Express server behind this build, so nothing in the web path may assume one.

- **One `/api/*` implementation.** `client/src/web/api.js` answers the subset
  the shell needs from the IndexedDB vault and the in-memory key store, using
  the M3a-1 error contract. The interception base is
  `import.meta.env.VITE_SAJAS_API_BASE || 'http://localhost:5000/api'`
  (`client/src/web/runtime.js`), and every request under it is answered
  locally by `client/src/web/install.js`, so web mode must never call the
  desktop server; the canary asserts that zero requests reach
  `http://localhost:5000`. Desktop-only routes are listed in `SERVER_ONLY` and
  must keep returning the typed `NOT_SUPPORTED_IN_WEB` payload — never an
  empty success or an untyped 404.
- **Key rules.** The plaintext key lives in a closure in
  `client/src/web/keyStore.js`; it must never touch `localStorage`,
  `sessionStorage`, cookies, URLs or logs. The only persistence is the optional
  encrypted blob in the `keyVault` store (PBKDF2-SHA-256, 600k iterations,
  AES-GCM, passphrase never stored), and the only request allowed to carry the
  plaintext key is HTTPS to `api.anthropic.com` in `x-api-key`.
- **Core imports.** Client code imports `@sajas/core` subpaths only (`errors`,
  `models`, `secrets`), so the Anthropic SDK stays out of the browser bundle
  until M3a-4.
- **Job feeds and tracker.** Feed code lives in `packages/core/src/feeds/`
  (pure) and `client/src/web/feeds.js` (network). The job feeds tab and the
  backup tab are web-only. `clearFeedCache()` must run on panic wipe. The web
  port accepts only `status`, `notes`, `applyUrl`, and `description` on job
  updates.
- **Merge gate.** `npm run test:web` serves the already-built `client/dist`
  with the production headers and runs the Playwright canary plus the offline
  feeds, tracker and backup flow; the `web` CI job treats it as
  merge-blocking (run `npm run build:web` first). The canary
  asserts the key appears only in the `x-api-key` header to
  `api.anthropic.com`, that no other origin is contacted, that the saved blob is
  ciphertext, and that Forget and panic wipe remove exactly what they claim.
- **CSP.** `client/public/_headers` is web-only: `script-src 'self'` and
  `font-src 'self'` forbid third-party scripts and fonts, and `connect-src`
  reserves `remotive.com`, `www.arbeitnow.com` and `jobicy.com` for later feed
  milestones. Do not add analytics, remote fonts or any other third-party
  origin to the web build.

### `callClaude` (`packages/core/src/ai.js`) and the server adapter (`agents/llm.js`)

`callClaude(req, hooks)` is the one place the suite talks to Anthropic. It validates the key first (`ClaudeKeyError` for a missing, Admin or malformed key; `ClaudeAuthError` on a 401; `ClaudePermissionError` on a 403, which maps to `KEY_PERMISSION` unless the error is really a spend cap), always streams, pins the client `baseURL` to `https://api.anthropic.com` (`ANTHROPIC_BASE_URL`, e.g. from a gateway configured for another tool, can never redirect the user's key), reads text only from `text` blocks (a response may begin with a `thinking` block), continues `pause_turn` server-tool turns up to `maxContinuations` (default 12), and throws `ClaudeRefusalError` on a refusal. A reply cut off by `max_tokens` (or `model_context_window_exceeded`) is returned as partial text with `truncated: true`. Refusals use the server-side fallback beta by default (`REFUSAL_FALLBACK_DEFAULT`, decided by smoke probe 5). `hooks.beforeCall` runs before every request (the adapter uses it for the demo gate and the budget check), `hooks.onUsage` after each response, `hooks.retryDelayMs` / `hooks.sleep` override the retry wait (tests), and `hooks.client` injects a client (tests use `fakeClient` from `@sajas/core/testing`).

**Self-degrading (M0.5).** Three assumptions were never verified against the live API (the M0 smoke test needs a real key): the refusal-fallback beta (`betas` + `fallbacks:'default'`), JSON-schema output together with server tools (web search), and web search on Haiku. If the API answers HTTP 400 to one of them, `callClaude` retries the request once without it (a fresh request on the same attempt index, so `hooks.beforeCall`, i.e. the budget guard, runs again and `maxContinuations` is not consumed): `refusal-fallback` (plain stream, no beta), `schema-with-tools` (drops `output_config.format`, keeps `effort`), `haiku-search` (Haiku swapped for Sonnet). `degradeStepFor(err, request)` is the pure classifier: it matches only a 400, only when the request really used the feature (beta path / tools + `output_config.format` / web-search tool on Haiku), only when the message contains one of the step's keywords, and (schema and Haiku steps) only on the first request of a call, so an unrelated 400 (bad model, malformed request) is rethrown untouched, a 401/403 is never retried, each step is used at most once per call, and a failed retry surfaces the retry's own error. A step is remembered process-wide (`getLearnedCapabilities()`; `resetLearnedCapabilities()` is for tests) only when the retried request SUCCEEDS, and later calls then skip the failing variant up front. `ClaudeResult.degraded` lists the steps applied in that call (empty when a lesson was already learned), and `hooks.onLog` reports each as `<task>: <step> not accepted by the API; retried without it` (the server adapter forwards it to the activity log). A lesson applied up front on a later call is announced once per process (`<task>: <step> was rejected earlier; running without it`; it makes a silent Haiku-to-Sonnet swap visible) and is not listed in `degraded`; each retry notice carries a scrubbed ~120-char excerpt of the API's error. The keyword matching is a heuristic: a wrongly matched 400 simply fails again on retry and nothing is learned. The learned state is per process and not persisted; `smoke-live.mjs` resets it before every probe and reports a probe as FAIL when `result.degraded` is non-empty (the API rejected the feature and `callClaude` papered over it), so the smoke run still tells the truth; `npm run smoke:live` is still how to settle the choices permanently (`CAPABILITIES`, `REFUSAL_FALLBACK_DEFAULT`).

**Retries (M3a-4).** The SDK client is pinned to `maxRetries: 0` so `callClaude` owns every retry decision. After the self-degrading step (if any), a transient failure is retried up to `maxRetries` times (default 2): HTTP 408, 409, 529 and any 5xx are retried; a 429 is retried only when the response carries `retry-after` (rate limits), never when it is a spend/credit cap; 401/403, validation and other 4xx are never retried. The wait honours `retry-after` (capped at 60s) or backs off exponentially, and `hooks.beforeCall` runs again before every retry, so the budget guard can stop the loop. `shouldRetryError` and `retryDelayMsOf` are pure and unit-tested.

`agents/llm.js` is the server-side adapter: `callLlm(profile, prompt, { maxTokens, schema, system, cacheSystem, bucket, effort })` returns text; `callLlmFull(profile, { task, prompt|messages, images, system, cacheSystem, schema, tools, maxTokens, effort, maxContinuations })` returns the whole result (used where tools or the conversation matter: AI search, research, referral search, computer-use); `callLlmVision` adds screenshots. `bucket` is the task key. The adapter supplies the API key from the merged profile, resolves the model, honours the toggles, enforces the demo gate and the daily budget, and writes every response to the usage ledger.

### Structured outputs & prompt caching

Both are user-toggleable in Settings (default ON); the adapter drops them when the toggle is off.

- **Structured outputs** (`profile.useStructuredOutputs`): `schema` is sent as `output_config.format = { type: 'json_schema', schema }` — constrained decoding that guarantees schema-valid JSON. Used by Agent 3 smart-fill (`SMARTFILL_SCHEMA` → `{ fills: [{fid,value}] }`, converted back to a mapping; a flat-object fallback keeps the toggle-off path working), the planner `planPage` (`PLAN_SCHEMA` in `pageBrain.js`), memory reflection/Dreaming and the AI search (`JOBS_SCHEMA`). Schemas need `additionalProperties:false` and listed `required`; dynamic-key objects are NOT allowed (hence the `fills` array shape).
- **Prompt caching** (`profile.usePromptCaching`): with `cacheSystem: true` a string `system` becomes one text block marked `cache_control: { type: 'ephemeral' }`; an array `system` is passed through untouched (the caller owns cache placement). Caching is a prefix match, so the cached prefix must be identical across calls: Agent 2's `system` (from `tailorPrompts.js`) holds only the injection shield, the base CV and the company-independent dossier digest, and is shared by the CV and cover-letter calls and by every job in a batch. A prompt shorter than the model's minimum cacheable length silently isn't cached. The adapter logs `Prompt cache: N read, M written` (type `system`) when a hit or write occurs.

### Cost per task and evals

`withTask(type, fn)` (`server/src/telemetry.js`) wraps each agent run — `hunt`, `tailor`, `apply`, `memory-reflect`, `memory-dream` — in an `AsyncLocalStorage` context (`db/taskContext.js`). `addUsage` attributes every AI call made inside it to that task and `recordTaskRun` counts runs and failures, so the usage summary can report cost per task, average cost per run and cache hit ratio (`GET /api/usage` → `today.byTask`; shown as "Cost per task (today)" in Settings → AI & Cost). Calls made outside any task still count toward the per-day and per-bucket totals.

`npm run eval` (`evals/run.mjs`) exercises the two quality-sensitive tasks (tailoring and the planner) against fictional fixtures with deterministic checks. The default run is DRY: `fakeClient`, no network, no key, no spend; it only proves the plan/estimate/result path. `--live --yes-spend` with `ANTHROPIC_API_KEY` in the environment runs it against the real API and costs money. `npm run smoke:live` is a separate set of live probes that also spends money (see Dev commands).

## Routines (T1), Dreaming (T2), computer-use (T3), parallel sub-agents (T4) & referral pipeline (T5)

- **Routines (T1, `routineRunner.js`)** — a **dependency-free** scheduler (60 s `setInterval` tick + an 8 s startup catch-up pass). `isDue(routine, now)` is a pure function over the clock: `daily`/`weekdays` fire once past `timeOfDay` if not already run since that slot (implicit catch-up; `catchUp:false` only fires within a 90-min window); `every_n_hours` fires on interval (1 h floor). One routine runs per tick, one at a time (module `busy` flag), and a routine **defers** (status `skipped`) if a manual hunt/apply is in progress — unattended work never collides with the user. `hunt` runs Agent 1; `hunt_and_tailor` then auto-tailors the top `autoTailorCount` NEW jobs (snapshot-diff of job IDs, skipped silently w/o a key) — **concurrently via `tailorJobsConcurrently` (T4), bounded by `tailorConcurrency`**; `dream` runs the Dreaming pass; `canary` (**T10**) runs `runCanarySession({})` for every enabled source and records `{ canary, tested, passed, note }` — it never hunts, tailors, applies or calls the AI, and it takes the `canary` browser lock itself: if a hunt/apply/login-check holds the browser it records `skipped` and returns without starting a session (the injectable seam is `__setCanarySessionForTests`). **Routines never run Agent 3 / never submit** — enforced in `ROUTINE_TYPES` and the runner. Best-effort: errors are caught and recorded on the routine, never crash the server. Started from `index.js` `app.listen`.
- **Dreaming (T2, `dreamOverMemory()` in `memoryReflect.js`)** — a periodic curation pass over the WHOLE dossier (distinct from per-application `reflectOnApplication`). Reads the application outcome log + win transcripts and returns `{reinforce:[idx], prune:[idx], add:[{text,category}]}` (DREAM_SCHEMA; via `callLlm`, task `memory`). Reinforce bumps insight `weight`; **prune never removes `source:'manual'` insights and is capped at half** the snapshot; adds land at weight 2. Gated by `profile.useDreaming` (default ON), key-skip silent, and an `insufficient-data` short-circuit (no call when there's nothing to learn). Triggers: a `dream` routine, the **Reflect now** button (`POST /api/memory/dream`), or directly.
- **Parallel sub-agents (T4, `pool.js` + `subAgents.js` + `companyResearch.js`)** — turns serial tailoring into bounded parallel bursts. `pool.js` is a **dependency-free** concurrency pool: `mapPool(items, worker, n)` runs ≤`n` workers at once, returns results in original order each shaped `{ok,value}`/`{ok:false,error}` so one failure never aborts the batch; `resolveTailorConcurrency(profile)` clamps `profile.tailorConcurrency` to **1–5** (this is the cost cap and the hook for a future tier gate). `subAgents.js` `tailorJobsConcurrently(jobIds,{concurrency,trigger})` runs in two phases: **(1) research fan-out** — if `useResearchFanout` is on, `mapPool`s `researchCompany()` over the jobs so the slow web-search step overlaps; **(2) tailor fan-out** — `mapPool`s `runDocumentTailorAgent(id,{researchBrief})` so each Agent 2 call reuses its pre-fetched brief (no double research). Batches are **hard-capped at 10 jobs**; it sets each job to `tailoring` up front and reverts to `found` only if nothing was saved (mirrors the single-job route). **`companyResearch.js`** `researchCompany(profile, job)` returns a compact grounded brief (employer sector, recent news, role priorities, SA salary context) via the Anthropic server-side `web_search` tool — **Anthropic-only**, `max_uses:3`, **best-effort (`''` on any failure / when disabled / keyless)**, gated by `researchFanoutReady()` (`useResearchFanout` true AND a real Anthropic key). The brief is threaded, as untrusted data (wrapped in `[BEGIN/END UNTRUSTED RESEARCH]` markers), into Agent 2's per-job CV and cover-letter prompts (not the cached system block) and referenced by the cover-letter prompt's "Why this company" guideline. **Consumers:** the `hunt_and_tailor` routine (replaces its serial auto-tailor loop) and `POST /api/jobs/tailor-batch` (+ a "Tailor all found" button in the Hunter tab). **T4 never runs Agent 3 / never submits** — same human-on-the-loop guarantee. Pure pool logic is unit-tested (order preservation, per-item error isolation, peak-concurrency bound, clamping).
- **Computer-use (T3, `computerUse.js`)** — `computerUseFillForm(page, profile, job, { maxSteps })` runs an Anthropic computer-use agentic loop bound to the existing Playwright page, using the `computer_toolset_20260801` toolset (GA: no beta header, no tool `name`, no display dimensions; zoom disabled). The model is the `computer-use` task's (Sonnet 5.5; `profile.computerUseModel` overrides it if it is an exact registry ID) and every request goes through `callLlmFull`, so the daily budget is checked before each step and usage is metered under `computer-use`. Wire format: Claude's calls are `tool_use` blocks whose `name` is the member action (screenshot, left_click, type, key, …) with `toolset_name: 'computer'`; a turn can hold several blocks, each answered by exactly one `tool_result` in order, and after the first failure the remaining blocks answer "Not executed". It runs as a **finisher after** the DOM `smartFillForm` (which stays the cheap, memory-capturing default), completing tricky/custom fields. Coordinates are mapped image-px → CSS-px via `devicePixelRatio`. **Submit-safety is enforced in code, not just the prompt:** every click is hit-tested (`elementTextAt`: the deepest element at the point, through open shadow roots and into iframes) and refused if the control's text is refused by `submitGuard.isRefusedForModel` (final-submit wording, account actions such as sign in / continue with Google, and the Apply family); a point that cannot be read (closed page, cross-origin frame, too many frames) is refused too (fail closed). Enter/Space keypresses are checked against what has focus (`keyPressVerdict`) and typed newlines/tabs outside a `<textarea>` become spaces (`planTyping`), so a keystroke can't submit a form either. Stops on CAPTCHA text and is bounded by `computerUseMaxSteps` (`resolveMaxSteps`: 1–40, default 20). Anthropic-only, `useComputerUse` default OFF (most token-hungry). Wired into Agent 3 via a local `fillForm(p)` helper used by both autopilot and the manual Smart-fill button. Pure helpers (`isSubmitText`, `mapKey`, `pngDimensions`, `computerUseSupported`, `resolveMaxSteps`, `keyPressVerdict`, `planTyping`) are unit-tested.
- **Referral pipeline (T5, `referralAgent.js`)** — the post-application **"Direct Outreach Channel"** (a counter-measure to ATS-only screening: open a human-to-human path to technical leadership after applying). `runReferralPipeline(profile, job)` runs two best-effort steps: **(1) `findReferralContact()`** — grounded discovery of ONE senior engineering contact (Engineering Manager → Tech Lead → Team Lead → Head of Eng → CTO) at the applied-to company via the Anthropic server-side `web_search` tool (same engine as `jobSearchAI`/`companyResearch`, task `referral-search`; `max_uses:3`, ZA-localized; `pause_turn` continuation is handled inside callClaude). It returns a normalized `{ full_name, exact_role, company, profile_url, grounded }` and **NEVER invents a person** — if there's no Anthropic key (`groundedReferralReady()` false), the search verifies nobody, or anything throws, it falls back to `{ full_name:'', profile_url: linkedInPeopleSearchUrl(company), grounded:false }` (a pre-filtered LinkedIn people-search link the user follows themselves). **(2) `draftOutreachMessage()`** — a <150-word peer-to-peer message via `callLlm()` (task `referral`), referencing the exact role, connecting the user's strongest technical strength (inferred from a capped `baseCv` excerpt + `keywords`) to the company, and ending with a CTA to `portfolioUrl`/`linkedInUrl`; a minimal non-empty template is used on failure so the channel is never blank. **Trigger:** manual only — the **"Find referral contact"** button on `status:'applied'` jobs in the dedicated **Direct Outreach** tab (`ReferralPanel` in `App.jsx`; the Apply Copilot control room links across to it), `POST /api/jobs/:id/referral` (awaited, saves `job.referral`). Cost-controlled by being click-to-run (web search billing) and self-gating to the free LinkedIn fallback without an Anthropic key. **T5 NEVER sends, connects, or messages anyone — it only drafts; the user reviews and reaches out** (same human-on-the-loop guarantee as the rest of the suite). Pure helpers (`linkedInPeopleSearchUrl`, `groundedReferralReady`) are unit-tested.

## Cost controls (T6): performance modes, usage ledger, daily budget & deep search

Built because real-world use was draining the user's API credit. Four cooperating pieces:

- **Performance presets** (`PERFORMANCE_PRESETS` in helper.js, applied via `POST /api/profile/preset`, rendered as `PresetCards` in Settings → AI & Cost): **Token Saver** (AI search on Haiku 5.5 — Sonnet 5.5 if `CAPABILITIES.haikuWebSearch` is false — at `searchDepth:'light'`, ALL optional AI off — planner/vision/computer-use/research/link-repair/reflection/dreaming — caching+structured on (free wins), concurrency 1, 2 kw × 1 loc), **Balanced** (the recommended defaults: standard depth, planner+memory+dreaming on, expensive extras off, concurrency 3), **Maximum** (deep 2-round search on Opus 5.5, link repair + research fan-out + vision + computer-use all on, concurrency 5, 5 kw × 3 loc). Presets never touch the API key, personal info, CV or answers. `detectActivePreset(profile)` reports which bundle the live values actually match (else `'custom'`) — returned by GET /api/profile as `performanceModeActual` and highlighted in the UI, so a hand-tweaked toggle can't masquerade as a preset. NO preset enables any auto-submit behaviour (unit-tested).
- **Usage ledger** (`addUsage` in helper.js + the `@sajas/core` estimator): every AI call from every feature records tokens/cache/web-searches into per-day, per-bucket (and, inside `withTask`, per-task) tallies with an ESTIMATED USD cost (clearly labelled estimates; the Anthropic invoice is ground truth). Rendered by `UsagePanel` (Settings → AI & Cost): est. spend today / last 7 days, tokens in/out, web searches, cache savings, per-feature badges, and a budget progress bar. `GET /api/usage`, reset via `DELETE /api/usage`.
- **Daily budget guard** (`profile.dailyBudgetUSD`, 0 = off): when today's estimated spend reaches the cap, `assertBudget()` in llm.js runs in callClaude's `beforeCall` hook, so `callLlm`/`callLlmFull`/`callLlmVision` REFUSE before EVERY request (clear log + `BUDGET_EXCEEDED` error) — including each `pause_turn` continuation and each computer-use step; the AI-search and link-repair entry points also check up front and skip with the same message. Hard stop until midnight or the cap is raised; the UsagePanel shows a red "budget reached" banner. Best-effort features degrade gracefully (they already catch); a manual Tailor click surfaces the budget message instead of spending.
- **Search depth / deep search** (`profile.searchDepth`, see jobSearchAI.js): the thoroughness dial — `deep` adds a second differently-targeted grounded round per keyword (the fix for "the hunter isn't looking thoroughly"), `light` is the Token-Saver setting. Echoed as a `depth:` badge in the Hunter tab's "Next run" strip.

## Security model

- `keys.json`, `browser-profile/`, `generated-docs/` and `supporting-docs/` are **gitignored** — never commit them (`supporting-docs/` holds the user's ID/qualification PDFs — sensitive PII).
- **T6 hardening:** (1) `addLog` runs every message through `scrubSecrets` — anything shaped like an Anthropic, OpenRouter or Google API key (core's `scrubSecrets` still scrubs all three shapes as defence in depth) is replaced with `•••redacted-key•••` before it reaches the UI log buffer or stdout (belt-and-braces against SDK error messages echoing a key). (2) `keys.json` is written with POSIX mode `0600` (no-op on Windows, tighter elsewhere). (3) Supporting-document uploads are capped at **15 MB** in `saveSupportingDocument` on top of the `%PDF` magic-byte check. (4) Every Danger-Zone bulk clear first snapshots db.json to `db.backup.json` (`backupDb`, 60s debounce so "Clear everything"'s four parallel clears keep ONE pre-clear snapshot) — restorable via Settings → Documents & Data → "Restore last backup" (`POST /api/backup/restore`). (5) The API binds to `127.0.0.1` (loopback only), not 0.0.0.0.
- **Local API guard (`server/src/localGuard.js`, mounted in `index.js` right after `cors`, before `express.json` and every route):** CORS only controls who may read a response, so on its own any web page open in the user's browser could fire a body-less POST at `127.0.0.1:5000` (start a paid hunt, restore a backup) and a rebinding hostname could reach the API. The guard refuses, with `403 {error}`: (1) a `Host` that is not `localhost` / `127.0.0.1` / `[::1]` on exactly the configured `PORT` (blocks DNS rebinding, even for GET); (2) an `Origin`, when present, whose hostname is not localhost (any port, because Vite runs on another one; no Origin is allowed for Electron/curl/same-origin); (3) any method other than GET/HEAD/OPTIONS without the header `X-SAJAS-Client: 1` (blocks cross-site form POSTs and simple requests, which cannot set a custom header, and forces a CORS preflight for everything else). `client/src/main.jsx` wraps `window.fetch` to add the header to every call to the API base; the demo fixture page and `scripts/demo.test.mjs` send it too. **Any new in-repo caller of a state-changing route (script, test, fixture) must send `X-SAJAS-Client: 1`.** The Electron renderer (loaded from `file://`) was verified to still work (GET and header-bearing POST both succeed). **Limits:** a web page can no longer fire state-changing (non-GET) requests or reach the API through a rebinding hostname, but the guard does NOT authenticate local processes (any local process that sends the header can call the API), and a page served from ANY localhost port can drive the API (cors and the guard allow localhost on every port). Because GETs need no header, a GET route must never write or launch anything (hence `login-status` is a POST).
- API keys travel only via the UI → `saveProfile()` → `keys.json`. The `process.env.*` fallbacks for keys were removed from `agent2-tailor.js`.
- `browser-profile/` stores session cookies, not passwords. When `channel: 'chrome'` is used on Windows, cookies are DPAPI-encrypted (tied to the local Windows user account).
- Agent 3 passes only `{ title, company, tailoredCvText, tailoredCoverLetterText, autofill, injectionWarnings, hasCvFile, hasSupportingDocs }` into the HUD `page.evaluate` — `baseCv`, API keys, and the supporting-document file paths/bytes are never sent into the portal page context (`hasSupportingDocs` is a plain boolean used only to render the attach button; the actual files are attached on the Node side via `setInputFiles`). (Smart-fill builds its LLM prompt on the Node side, so `baseCv` is used there but never injected into the page.)

## Key implementation notes

- Server uses **ESM** (`"type": "module"` in `server/package.json`). Use `import`/`export`, not `require`. `electron/main.js` intentionally stays CommonJS.
- `DB_PATH`, `KEYS_PATH`, `BROWSER_PROFILE_PATH`, `GENERATED_DOCS_PATH` and `SUPPORTING_DOCS_PATH` env vars are injected by `electron/main.js` → `startServer()` (all under `app.getPath('userData')`). In dev they fall back to the project root.
- **Electron window loading (`electron/main.js`) — blank-window hardening**: `isDev = !app.isPackaged` is true for ANY unpackaged launch (`npm run electron:start`, `electron .`), which used to load `http://localhost:4173` even when Vite wasn't running → a silent blank window. `createWindow()` now (1) probes the dev URL with `isUrlReachable()` first and only uses it if actually up; (2) **falls back to the built `client/dist/index.html`** when the dev server is down but a build exists; (3) registers a `did-fail-load` handler + `showLoadError()` that renders a readable error page (with the "run `npm run electron:dev`" hint) instead of leaving the window blank; (4) wraps the load in try/catch so a rejected load promise can't become an unhandled rejection. **For dev, always use `npm run electron:dev`** (starts Vite + Electron together via `wait-on`); standalone Electron now falls back to `dist/` instead of going blank. `client/dist/` must be built (`npm run build:client`) for the packaged/fallback path.
- **Single React instance (`client/vite.config.js`)**: `optimizeDeps.include: ['react','react-dom','react-dom/client','react/jsx-runtime','react/jsx-dev-runtime']` + `resolve.dedupe: ['react','react-dom']`. This pre-bundles every React entry point in **one** optimize pass so react and react-dom can't land on mismatched dep-optimization generations — the cause of a runtime **"Invalid hook call / Cannot read properties of null (reading 'useState')"** crash (white screen) that came from a stale `client/node_modules/.vite` cache serving react and react-dom under different `?v=` hashes (different React instances → null hook dispatcher). If it recurs: stop the dev server, `rm -rf client/node_modules/.vite`, restart (changing `vite.config.js` also auto-invalidates that cache on next start). Electron's renderer caches modules like a browser, so apply fixes by **restarting** the Electron session, not just reloading.
- Agent 1 uses a **fresh page per source** — a bot-block on one board does not affect the page context used by another. Page timeout is 20 s. Page title is logged after each navigation to detect Cloudflare blocks or login redirects. Card count below the score filter and rejected non-SA count are logged separately.
- **Registry pipeline (`hunter/`)** — the 12 `scrapeXxx` functions are gone; the hunter iterates `SOURCES` in `hunter/registry.js` (id/name/scope/tier/`saCheck`/`waitIdleMs`/pagination/`buildUrl`/`extractInPage`/canary/optional `skipJsonLd`/`linkless`/`needsLogin`). `queriesFor()` expands each source's scope (perLocation → keyword × location; oncePerKeyword/noLocation → keyword × `null`), and each query runs through `crawlPages()` (`hunter/crawl.js`) at `pageCapForDepth(profile.searchDepth)`: **light 1 / standard 2 / deep 4** pages, 2 s page spacing, a 60 s/query budget, and stops on blocked/error/exhausted/saturated/page-cap/time/stopped. **Pagination** is declared per source as `pagination: { param, firstValue, step, verified: false }`; `buildUrl(query, pageNo)` (through `sources/util.js` `withPageParam`) replaces or appends `param=firstValue + step*(pageNo-1)` exactly once, and `param: null` means the source has none (Google Jobs, Gumtree). Current params: LinkedIn/Indeed `start` (0 + 25 / 0 + 10), PNet/CareerJunction/Executive/JobPlacements/GovZA/JobMail/Jobs.co.za `page` (1 + 1), Adzuna `p` (1 + 1). Every parameter stays `verified: false` until a live run confirms the site honours it (see the live-verification baseline). Pages are de-duplicated by apply URL (else title+company). `fetchSourcePage()` (`hunter/runner.js`) never throws: every failure (HTTP error, navigation error, block) is returned in `meta.error`/`meta.blocked`; a blocked page's items are discarded. JSON-LD fallback and the 80-card cap run per fetched page, while `saCheck` filtering, scoring, `validateJobs` and `finalizeAndSave` run once per query over the de-duplicated items.
- **Source health + circuit breaker (`health.js` / `healthStore.js`)** — every source run is summarised with `summariseRun()` and persisted with `recordRun()`; `computeStatus()` drives `status` (`healthy|degraded|broken|blocked|needs-login|disabled|unknown`), and `shouldSkip()` makes the hunter log `⏭ <name> skipped: <reason>` and record `perSourceStats[name].skipped` without opening a page. Three consecutive broken runs open the circuit; two consecutive non-login blocks set a 6 h cooldown. A source that throws is recorded as an error run and never aborts the other sources.
- **Canary checks (`hunter/canary.js`, T8)** — `runCanary(page, source)` fetches page 1 with the source's `canary` keyword/location and returns `{at, pass, reasons, raw, ms, blocked, error}`; `reasons` short-circuits on a block (`blocked: <kind>`), then an error (`error: <msg>`), then the count (`returned <n> items, expected at least <minItems>`) and completeness (`only <x>% of items have title and link` — title only for `linkless` sources). `runCanaries({ ids, newPage, sleep, onResult, sources })` is sequential, 2 s apart, skips disabled sources silently, records every result with `recordCanary` and closes each page it opened. `runCanarySession({ ids, onResult })` launches the persistent profile headless (Chrome, then bundled Chromium: the hunter's options) and closes it in `finally`, but does NOT take the lock — `POST /api/hunter/sources/test` owns `canary`, a `canary` routine acquires/releases `canary` itself (T10), and `canaryStartRefusal()` is the pure 409 logic. The dashboard's source board (`GET /api/hunter/sources`) is read-only over these entries; PATCH only flips `enabled`/`resetCircuit`. Neither GET nor PATCH launches a browser.
- **Record tool + recorded fixtures (T10, `scripts/hunter-record.mjs`)** — `node scripts/hunter-record.mjs <sourceId> [--keyword <kw>] [--location <loc>] --yes` records page 1 of one source: it prints that it visits the live site, loads the URL from `source.buildUrl` in headless Chrome (Chrome first, bundled Chromium fallback) and a fresh browser context carrying the hunter fingerprint (UA, 1366×768, en-ZA, Africa/Johannesburg; `domcontentloaded`, then `min(waitIdleMs, 5000)`), sanitises the HTML with the exported pure `sanitizeHtml` and writes `server/src/hunter/fixtures/recorded/<id>-<yyyymmdd>.html`. It refuses without `--yes`, defaults the keyword to `developer` (location to the source's canary location), and does no DB write, no browser lock and no AI. The recorded directory is gitignored; `sources.contract.test.js` exports `recordedFixtures(sourceId, dir)` (sorted `<id>.html` / `<id>-*.html`, `[]` when absent) and adds one per-source test that skips when no recording exists, otherwise asserts every recorded page yields ≥1 well-formed item (non-empty title, string `applyUrl`, absolute unless `linkless`).
- **AI page-extractor fallback (`hunter/aiExtract.js`)** — when the **first page of a source's first query** yields 0 raw cards, is not blocked and has no error, and the source has a good baseline (`baselineRaw().median >= 3`) or already reads broken/degraded, one Haiku call reads the page text + visible anchors. Returned `applyUrl`s are kept only when they exactly match an on-page anchor. Gated by `profile.useAiExtractFallback`, an Anthropic key, and a shared `EXTRACT_CAP` of 6 attempts per run; extracted cards set the source's `via` to `ai-extract`.
- **Browser lock (`hunter/browserLock.js`)** — the persistent profile can only be opened by one Chromium, so `tryAcquireBrowser(kind)` (`hunt|canary|login-check|apply`) guards it. `POST /api/jobs/hunter` takes `hunt` before responding (409 `A browser job is already running (<owner>).`) and releases in `.finally`; apply takes `apply` and releases with its state reset; login-status takes `login-check` around its single-flight. A direct `runJobHunterAgent()` call acquires only when the lock is free, returns a zeroed result when another kind holds it, and never releases a lock it did not take.
- After each fetched page, Agent 1 runs `scrapeJsonLd()` against the same loaded page to harvest any embedded **schema.org/JobPosting** structured data. This is a resilience net against CSS class churn. Skipped for Google Jobs and Govt SA (no JobPosting JSON-LD).
- **Link validation (`linkValidator.js`, Agent 1) — conservative, keep-on-doubt**: before any job is saved (both the AI-search phase and the scraper phase), candidate links pass through `validateJobs()`. The design principle is **trust the grounded search; only remove what is provably useless** — never throw away a good job because a bot-wall or an unusual URL shape made it hard to verify. **One owner of link policy** (jobSearchAI no longer blanks URLs). Behaviour: (1) `classifyPostingUrl(url)` is a **lenient** shape check — it returns false only for clear non-postings (bare domain, `?q=`/`search=`, `/search|/browse|/results`, `"/in-place"` category with no id); a real posting URL of almost any board shape passes (e.g. a LinkedIn `/jobs/view/<slug>-<id>` passes because it carries an id). (2) `probeLink(url)` is a liveness fetch (follow redirects, browser UA) that declares **`dead` only on a high-confidence signal — HTTP 404/410/451 or an explicit "expired/filled/closed/no-longer-available" page**; every other non-2xx (401/403/405/429/5xx/999), timeout, network error, or ambiguous redirect-to-home/search is kept as `linkStatus:'unverified'`. **Drop/keep rules:** a job is DROPPED only when its link is confirmed dead; a search/category "link" has its URL **stripped** and the job is kept as a **linkless lead** (`linkStatus:'no-link'`, so Agent 3 won't open it and can't wander); everything else is kept (`live`/`unverified`). Kept jobs gain `linkStatus` + `linkCheckedAt`, surfaced as a green **Verified** / amber **Unverified** `LinkBadge` on job cards (Dashboard, Hunter table, Tailor detail; `no-link`/unchecked render no badge). Bounded concurrency via `pool.js` `mapPool`; best-effort (returns jobs unvalidated on its own failure, and a single worker error keeps that job flagged `unverified` rather than losing it). Gated by `profile.useLinkValidation` (default ON; Settings toggle "Verify job links before saving"); with liveness off it still strips obvious search/category links (free URL hygiene) but probes nothing. **History:** an earlier version of this gate was far too aggressive — strict per-board URL regexes that *blanked* real postings (which then got dropped as "no url"), plus treating any 4xx/5xx/redirect as dead — which gutted the AI search and made the hunter look broken; this rewrite is the fix.
  - **Browser-grade probing**: the hunter creates ONE `createProbeContext()` (a Playwright `request.newContext()` — realistic TLS/headers, no browser window) and threads it through every `probeLink`/`validateJobs` call (both phases), so bot-walls cause far fewer false `unverified` flags than a raw `fetch`. Falls back to Node `fetch` if the context can't be created. Disposed in the hunter's `finally`.
  - **AI link repair (`findDirectPostingUrl`, opt-in)**: when a kept job has **no usable link** (`no-link`), the hunter can ask Claude — grounded web search — for the real posting URL, then **re-validate that URL** before saving (so a hallucinated/dead repair can't slip through). Gated by `profile.useLinkRepair` (default OFF — billed per search) + a real Anthropic key, and hard-capped at `LINK_REPAIR_CAP` (6) repairs per run. Repaired jobs are logged and counted.
  - **Run-level link health**: the hunter returns `linkStats` (`{ live, unverified, noLink, dead, repaired }`) inside `hunterState.lastResult`; the dashboard **RunSummary** renders it as a "Link health:" badge row.
  - **Re-validation (`revalidateJobLinks`, `POST /api/jobs/revalidate`)**: postings die over time, so the user can re-check links of **already-saved** jobs (statuses `found`/`tailored`/`tailoring`) from the **Re-check links** button (Hunter tab). It updates each job's `linkStatus` in place — a now-dead posting is flagged `linkStatus:'dead'` (red **Expired** `LinkBadge`) but **never deleted**; the user decides. Background, browser-grade, idempotent (a `revalidating` in-flight guard returns 409).
- **AI search engine (`jobSearchAI.js`)**: `huntViaClaudeSearch()` runs FIRST in `runJobHunterAgent` (Phase 0), using the Anthropic server-side `web_search_20260318` tool (core's `webSearchTool`) with `user_location` country `ZA`. It's **grounded** — Claude returns real source URLs from its search, and the prompt forbids inventing jobs/URLs; results without an `http(s)` `applyUrl` keep the title but no link. The prompt **strongly prefers major boards/ATS** and asks for the canonical posting page (a board's job page is acceptable) — it deliberately **no longer tells Claude to *drop* a job when the link isn't a perfect direct posting** (that both shrank yield and produced linkless jobs); instead it returns the job with `applyUrl:""` and the downstream validator decides. Each result's `source` is set from its URL host (`sourceFromUrl` → LinkedIn/PNet/Indeed/Greenhouse/…, else the employer domain) so obscure aggregators are visible, and results are **sorted major-board-first** (`boardRank`) so they win de-duplication. Requires `profile.anthropicApiKey`. Gated by `profile.useAiSearch` (default true); model `profile.aiSearchModel` when it is an exact registry ID, else the `ai-search` task default (Sonnet 5.5). Billed ~$10/1,000 searches; at the default `standard` depth `max_uses: 5` per keyword, up to **20 results** per keyword. The Playwright scrapers run after as best-effort fallback.
